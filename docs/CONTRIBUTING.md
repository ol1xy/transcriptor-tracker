# Руководство по участию в разработке (Contributing Guide)

Добро пожаловать в проект **Transcriptor-Tracker**! Этот документ описывает правила совместной работы, стандарты оформления кода и процесс слияния изменений для нашей команды из двух человек.

Мы придерживаемся принципов **FOSSDEV** (разработка свободного ПО): прозрачность процессов, обязательное тестирование и рецензирование кода через Pull Requests.

---

## 1. Работа с ветками в Git

Прямая работа в ветке `main` запрещена. Вся разработка ведется через создание тематических веток (feature branches) относительно актуального состояния `main`.

### Схема именования веток:
* `feat/короткое-название` — для добавления новой функциональности (например, `feat/transcribe-core`).
* `fix/короткое-название` — для исправления ошибок (например, `fix/whisper-timeout`).
* `docs/описание` — для работы с документацией и ежедневными отчетами (например, `docs/activity-log`).

---

## 2. Стандарты сообщений коммитов (Conventional Commits)

Каждое сообщение коммита должно быть информативным и следовать единому стандарту: `<тип>: <описание на английском языке>`.

### Допустимые типы (types):
* `feat` — добавление нового функционала.
* `fix` — исправление ошибки в коде.
* `docs` — изменения в документации (включая ежедневные записи).
* `test` — добавление или изменение тестов.
* `refactor` — изменение структуры кода без изменения его поведения.

### Примеры коммитов:
* `feat: added the BaseTrackerAdapter interface.`
* `test: written unit tests for the Pydantic resume model.`
* `docs: added work plan for day 3`
* `fix: fixed empty list validation in SummaryModel`

---

## 3. Процесс ведения ежедневных записей (Activity Log)

Для фиксации результатов работы и планов по SMART на каждый день мы используем следующий регламент:
1. Ежедневные планы и отчеты оформляются в папке репозитория: `docs/activity_logs/`.
2. Шаблон файла отчетов: `Ежедневные_Записи_ФамилияИмя.docx` (или дублирующий файл `docs/activity_logs/activity_log.md` в Markdown для удобства ревью).
3. Изменения в отчет вносятся в отдельной ветке `docs/activity-log` и сливаются в `main` через Pull Request в конце каждого рабочего дня.

---

## 4. Процесс отправки изменений (Pull Request Workflow)

Ни одно изменение не должно попасть в ветку `main` без код-ревью напарника.

### Шаг 1: Подготовка ветки
Перед открытием PR убедитесь, что:
* Код соответствует требованиям спецификации (`specification.md`).
* Локально запускается линтер и статический анализатор.

### Шаг 2: Тестирование и покрытие
Перед отправкой изменений запустите тесты и проверьте уровень покрытия кода:
```bash
make test
```
*Минимально допустимый порог общего покрытия кода (coverage) для слияния PR составляет **80%**.*

### Шаг 3: Создание Pull Request
1. Отправьте ветку в удаленный репозиторий: `git push origin feat/your-feature`.
2. Создайте Pull Request в ветку `main`.
3. Назначьте своего напарника в качестве **Reviewer (Рецензента)**.

### Шаг 4: Код-ревью (Review)
Рецензент обязан:
1. Проверить логику работы кода и его соответствие архитектурным границам.
2. Проверить сообщения коммитов на соответствие разделу 2 настоящего руководства.
3. Убедиться в наличии тестов на новый функционал.
4. Оставить конструктивные комментарии (если требуется доработка) или утвердить изменения (`Approve`).

Слияние ветки в `main` разрешается только после получения как минимум одного одобрения (`Approve`) и при условии успешного прохождения всех автоматических тестов.
